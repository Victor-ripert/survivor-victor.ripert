1. L'ordre annoncé
------------------------------------------------------------------------------
ORDER BY "updatedAt" DESC, "id" ASC — deux colonnes, la seconde unique.

Il est construit par buildCatalogueOrderBy() dans
packages/api/src/services/catalogue.filters.ts, appliqué par défaut par le
validateur (packages/api/src/validators/recruiter.ts) et publié dans
packages/api/openapi.yaml. Index correspondant, colonne pour colonne :

  CREATE INDEX "Profile_updatedAt_id_idx" ON public."Profile" USING btree ("updatedAt" DESC, id)

Plan d'exécution réellement choisi pour la requête de page :

                                                    QUERY PLAN                                                   
  ---------------------------------------------------------------------------------------------------------------
   Limit  (cost=0.55..2.81 rows=3 width=34)
     ->  Nested Loop  (cost=0.55..347.65 rows=460 width=34)
           ->  Index Scan using "Profile_updatedAt_id_idx" on "Profile" p  (cost=0.27..140.10 rows=464 width=60)
                 Filter: ("moderationStatus" <> 'REJECTED'::"ModerationStatus")
           ->  Index Scan using "User_pkey" on "User" u  (cost=0.27..0.45 rows=1 width=26)
                 Index Cond: (id = p."userId")
                 Filter: ("isActive" AND (role = 'APPLICANT'::"UserRole"))
  (7 rows)
  

Ce plan porte un nœud Sort, et il faut le dire plutôt que le passer sous
silence : sur 500 lignes, lire la table entière coûte moins cher que
descendre l'index, et le planificateur a raison. L'index n'est pas décoratif
pour autant — il sert bien l'ordre demandé, ce qui se vérifie en retirant au
planificateur le parcours séquentiel. Le nœud Sort disparaît :

                                                    QUERY PLAN                                                  
  --------------------------------------------------------------------------------------------------------------
   Limit  (cost=0.27..0.94 rows=3 width=34)
     ->  Index Only Scan using "Profile_updatedAt_id_idx" on "Profile" p  (cost=0.27..111.16 rows=500 width=34)
  (2 rows)
  

Les mesures au volume de recette (50 000 profils) sont dans
docs/preuves/EW-5-index-catalogue.txt et docs/decisions/02-index-du-catalogue.md.

Le déterminisme, lui, ne dépend d'aucun de ces deux plans : il tient à ce que
l'ORDER BY porte une clé unique en dernière position, donc à ce qu'aucune
paire de lignes ne soit à égalité. Un changement de plan réordonne le travail,
pas le résultat.
