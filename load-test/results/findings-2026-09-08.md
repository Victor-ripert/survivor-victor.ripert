## Result 1: the realistic baseline shows no performance bottleneck

| Route                          | p50     | p95     | max    |
| ------------------------------ | ------- | ------- | ------ |
| `GET /api/recruiter/catalogue` | 20.5 ms | 38.0 ms | 1.36 s |
| `GET /api/profiles/:id`        | 8.9 ms  | 16.7 ms | 436 ms |
| `GET /api/profiles/:id/videos` | 5.8 ms  | 12.3 ms | 41 ms  |

6968 requests, 55.5 req/s, 4007 completed iterations, 0 request timeouts, 0 5xx responses.
The only failures (2.59%, all on `profile_detail`) are the already-documented visibility gap
(`load-test/README.md`, "Known issue" section) — `PENDING` profiles the catalogue lists but the
single-profile route 404s on — not a performance problem.

**Why "no bottleneck found" isn't the end of the story:** with 0.5-2s of think time between
requests, 100 VUs never actually have more than a handful of requests in flight at once — a VU
spends most of its iteration sleeping, not waiting on the API. That pacing is realistic for a
recruiter clicking through a catalogue, but it also means the baseline alone under-tests any
resource with a low concurrency ceiling. Removing the pacing to find out was worth the extra 45
seconds.

## Result 2: the connection pool saturates once concurrency is real

Same scenario, same dataset, think time forced to 0 so all 100 VUs issue requests back-to-back:

| Route                          | p50 (baseline → stress)    | p95 (baseline → stress)    |
| ------------------------------ | -------------------------- | -------------------------- |
| `GET /api/recruiter/catalogue` | 20.5 ms → 226 ms (**11x**) | 38.0 ms → 425 ms (**11x**) |
| `GET /api/profiles/:id`        | 8.9 ms → 491 ms (**55x**)  | 16.7 ms → 750 ms (**45x**) |
| `GET /api/profiles/:id/videos` | 5.8 ms → 301 ms (**52x**)  | 12.3 ms → 438 ms (**36x**) |

Confirmed the cause directly rather than inferring it from latency alone: sampled
`pg_stat_activity` (as the API's own `DATABASE_URL` connects — not `docker compose exec`, which
reaches a different Postgres instance in this environment) every 3-4s during the stress run.

```
12:23:31.913Z  active=1  idle=6   idle-in-transaction=4    → 11 total
12:23:36.362Z  active=2  idle=4   idle-in-transaction=5    → 11 total
12:23:40.754Z  active=1  idle=3   idle-in-transaction=7    → 11 total
12:23:45.142Z  active=1  idle=4   idle-in-transaction=6    → 11 total
```

Every sample sums to **11** — the API's pool (10) plus the one connection the probe itself opened.
**Root cause:** `packages/api/src/config/prisma.ts` constructs `PrismaPg({ connectionString:
env.DATABASE_URL })` with no `max` option, so the underlying `pg.Pool` uses `node-postgres`'s
default of 10 connections. Under back-to-back load, all 10 fill up (several sitting "idle in
transaction" — a connection mid-transaction can't serve another query, so that's queueing time on
top of the pool being merely full) and every further request queues for one to free up. That
queueing is the entire ~11-55x latency increase above — no query got slower, requests just wait
longer for a connection before they can even start.

## Not yet fixed

This ticket is the baseline + diagnosis; the fix (raising the pool size, most likely via a `max`
option and re-running this same stress scenario for a before/after comparison) is the next one.
