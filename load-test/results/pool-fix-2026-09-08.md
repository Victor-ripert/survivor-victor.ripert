# Connection pool fix — before/after (2026-09-08)

Follows [`findings-2026-09-08.md`](findings-2026-09-08.md), which diagnosed the bottleneck this
fixes: `packages/api/src/config/prisma.ts` built its `pg.Pool` with no `max`, so it defaulted to
`node-postgres`'s own default of 10 connections, confirmed saturated (via `pg_stat_activity`)
under a synthetic zero-think-time 100-VU burst.

## The fix

Added `DATABASE_POOL_MAX` (`packages/api/src/config/env.ts`, default `20`), passed as `max` to
`PrismaPg` (`packages/api/src/config/prisma.ts`). 20 rather than something larger: Postgres's own
`max_connections` is 100 by default, shared with pgAdmin, migration/seed scripts, and headroom for
a second API process — handing one pool the whole ceiling would just move the failure mode
elsewhere.

## Before / after — same synthetic burst scenario

Same machine, same 500/300 dataset, same command
(`k6 run -e MIN_THINK_TIME_SECONDS=0 -e MAX_THINK_TIME_SECONDS=0 -e DURATION=45s load-test/catalogue.js`),
only `DATABASE_POOL_MAX` (implicitly 10, unset, before the fix — 20 after) differs.

| Route                          | p95 before (`before-pool-fix-2026-09-08.txt`) | p95 after (`after-pool-fix-2026-09-08.txt`) | Change |
| ------------------------------ | --------------------------------------------- | ------------------------------------------- | ------ |
| `GET /api/recruiter/catalogue` | 425 ms                                        | 369 ms                                      | -13%   |
| `GET /api/profiles/:id`        | 750 ms                                        | 608 ms                                      | -19%   |
| `GET /api/profiles/:id/videos` | 438 ms                                        | 361 ms                                      | -18%   |

Real, measured, and worth keeping — but **partial**, not a full fix, and the report should say so
plainly rather than round up:

- `pg_stat_activity`, sampled the same way as in the diagnosis, confirmed the pool is still the
  ceiling after the fix too — every sample summed to 21 (20 + the one probe connection) during the
  stress run, exactly as it summed to 11 (10 + probe) before. Raising the number moved the wall; it
  didn't remove it.
- An exploratory run at `DATABASE_POOL_MAX=50` (not committed — informal, to see where returns
  flatten) improved `profile_detail`/`profile_videos` further (p95 ≈ 425 ms / 268 ms) but left
  `catalogue` roughly unchanged (≈ 394 ms), which is a different signal — that route's own query
  cost, not queueing for a connection, may be what dominates for it at this concurrency. Not
  investigated further here.
- A meaningful share of connections sat `idle in transaction` during every stress run (both before
  and after — e.g. 4-10 of the pool at a time), despite none of the three read-only routes tested
  here wrapping a query in `prisma.$transaction`. Unexplained; worth a follow-up look at whether
  Prisma 7's driver adapter holds transactions open for plain reads, since a connection stuck
  `idle in transaction` can't serve another request regardless of pool size.
- **The realistic baseline (with think time — what a real 100-recruiter session looks like) never
  needed this fix**: `findings-2026-09-08.md`'s numbers (p95 12-38 ms across all three routes) were
  already healthy at the old default of 10. This fix hardens against a traffic _spike_ — many
  requests arriving with little pacing between them — not a problem the literally-requested
  "100 concurrent recruiters browsing" scenario was hitting.

## Honest summary

`DATABASE_POOL_MAX` went from an accidental, undocumented 10 to a deliberate, documented,
overridable 20 — a real and measured 13-19% p95 improvement under sustained burst load, confirmed
by direct connection-count sampling, not just latency numbers. It is not a complete fix: the pool
is still the ceiling at 20, and a distinct, unexplained "idle in transaction" pattern and a
possibly query-cost-bound catalogue route remain open questions past what this ticket investigated.
